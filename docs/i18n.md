# Internationalization (i18n)

omaset speaks the desktop language. The window, the human CLI, and the
engine's status messages resolve through one shared catalog set in `i18n/`
at the plugin root — the same directory Lua and QML read, so every frontend
agrees.

Only human-facing strings localize (the same line Omarchy's `omarchy`
command draws): setting/panel/section labels, option labels, and
status/result messages. Values, command names, flags, argument
placeholders, JSON/`--plain` output, and the MCP contract stay English,
because they are the machine contract.

## Where strings live

- **English source** — the `label`/`description`/`options` in
  `share/settings/*.lua`, plus the chrome strings in `en.json`. The
  engine serves English labels in `schema`/`get`/`help` regardless of the
  UI language; frontends localize at render time.
- **Canonical catalog** — `i18n/en.json`, regenerated by
  `scripts/i18n-extract`. Never edit it by hand.
- **Translations** — `i18n/<code>.json`, one flat JSON file per language.
  Filenames match Omarchy's registry codes (`pt-BR`, `zh-CN`, `es-MX`,
  `pt`, …). `i18n/es-MX.json` is the worked example.

Keys are stable ids, never sentences:

| Key | What it covers |
|---|---|
| `panel.<id>` | Sidebar / panel titles |
| `section.<panel>.<key>` | Presentational headers (`section()`'s key) |
| `setting.<id>` | Setting labels |
| `setting.<id>.description` | Setting descriptions |
| `setting.<id>.<sub>` | Group sub-setting labels |
| `setting.<id>.<sub>.description` | Group sub-setting descriptions |
| `setting.<id>.option.<value>` | Enum / choice labels. `<value>` is the stored token (`dwindle`, `top`, `on`, `300`, …) — the label is display-only. |
| `ui.*` | Window chrome (`ui.search`, `ui.workspace`, …) |
| `help.*`, `footer.*`, `unit.*` | Help overlay, footer hints, durations |
| `pref.<key>` (+ `.description`, `.option.<value>`, `.now`) | Preferences overlay labels |
| `cli.*` | CLI status/error strings (`cli.unknownSetting`, …) |

A value is a string, or a **plural object** for counted strings
(`ui.settingsFound`, `ui.changedCount`, `unit.hour`):
`{ "one": "%1 setting found", "other": "%1 settings found" }`.
`%1`/`%2` holes are substituted by the resolver (numbers go through
`formatNumber`), so translators may reorder them freely.

Resolution layers `en` → base language (`pt-BR` → `pt`) → language, the
same shape `Commons.Translations` uses. A missing key, or an empty
string, falls back to English at render time. Shipping English values in
a skeleton catalog is therefore safe.

## Language resolution

The language is read from Omarchy's own source of truth, never persisted
by omaset. Precedence (first valid wins):

1. `--lang <code>` on the CLI (`omaset --lang fr list`, `--lang=fr`)
2. `OMASET_LANGUAGE` env
3. The file at `OMARCHY_LANGUAGE_FILE` (or `~/.config/omarchy/language`) —
   what *Setup → Language* and `omarchy language` write
4. `en`

`omaset --lang list` prints the registry (`native name ⇥ code ⇥ English
name`). `omaset --lang <code>` with no command prints the resolved code.

The settings window follows the desktop language by default. For a
one-off preview (e.g. testing translations) `omaset ui --lang <code>`
(or `OMASET_LANGUAGE=<code> omaset ui`) writes the code to
`~/.config/omaset/ui-language` and summons the window in that language
for that launch only. The window's own resolver (`ui/UiTranslations.qml`)
reads that file plus `locales.json` (numbers, RTL, AM/PM), so the OS
language, `LANG`, and every other Omarchy surface stay untouched. Every
plain `omaset ui` clears the file before summoning, so the next launch
always starts on the desktop language again.

The locale registry itself is Omarchy's
`$OMARCHY_PATH/default/i18n/locales.json` (`formatLocale`, `decimal`,
`zeroDigit`, `direction`). omaset never duplicates it. Number formatting
(decimal separator, digit shape — e.g. Bengali digits) and plural rules
mirror Omarchy's `plural.jq`/`Plural.js` exactly; `tests/test_i18n.sh`
keeps the Lua port in agreement.

RTL languages (`ar`, `fa`, `he`, `ur`) read the window mirrored: the
whole window enables `LayoutMirroring` (sidebar and controls flip,
sliders and toggles throw the mirrored way, and `h`/`l` + arrows follow
the reading direction). This is the same idiom as Omarchy's
`OverlayWindow`. Meridiem markers (`AM`/`PM`) are *not* in any catalog —
the window takes them from `Qt.locale(...).amText/pmText`, like the bar
clock's `AP` token. CLI/MCP keep canonical `HH:MM`.

Engine-side, `lib/omaset/i18n.lua` provides `t()`, `tn()`,
`formatNumber()`, and `plural_category()`. QML uses the window's own
`ui/UiTranslations.qml` (a small resolver with a writable `language`, so
`omaset ui --lang` can preview a language without touching the desktop)
plus `Commons.I18n` for the registry/language fallback.
`ui/model.js` receives `tn`/`formatNumber` as parameters — the same
threading idiom Omarchy's own model files use.

## The per-release checklist (agents: read this)

When a new version of Omarchy lands, do this — in this order:

1. **New setting?** Add the English `label`/`description`/`options` in
   `share/settings/*.lua`. That English text *is* the fallback; no other
   change is needed for correctness.
2. **Option value changed or renamed** (e.g. 4.5's layout `dwindle` shown
   as "Tiling", `bar.transparent` → `bar.background`)? The `option`
   entries follow the stored `value`; only the label text changed. If a
   token was added or removed, the key list changes with it. Stored
   values (`dwindle`, `top`, `on`) are never translated.
3. **Channel-gated settings** (e.g. `master` only pre-4.5)? The canonical
   catalog covers *both* capability branches: the extractor runs the
   schema under `OMASET_WORKSPACE_MODES=1` and `=0` and unions the keys.
   What looks stale is often the other branch.
4. **Regenerate the canonical English:**
   `scripts/i18n-extract`. This rewrites `i18n/en.json` (sorted, 250
   keys at last count). Commit the diff.
5. **Update the translations.** For every new/changed English key, update
   the affected `i18n/<code>.json` files — or leave them untranslated
   (the resolver falls back to English). For a brand-new language,
   `scripts/i18n-extract --skeleton <code>` writes a complete skeleton
   with that language's plural categories pre-filled. Never delete a key
   just because the English changed; the shape is stable.
6. **Validate:** `tests/test_i18n.sh` (also runs in `tests/run.sh`). It
   checks the canonical catalog is fresh, every registry code has a
   catalog (and no extras), every catalog covers exactly the English
   keys, `%N` placeholders are preserved, and each plural entry carries
   the categories its language needs.
7. **Reload + eyeball:** `omaset ui reload`, then `omarchy language
   <code>` and open the window — sidebar/content, footer counts,
   `?` help, Changed, and Preferences.

## What is never translated

- Stored values in config files and JSON output (`"dwindle"`,
  `"bar": {"position": "top"}`, `"on"`, `300`)
- Command/subcommand names, flags (`--plain`, `--json`, `--all`, `--lang`),
  argument placeholders (`<id>`, `<key>`)
- The `--help` skeleton (`USAGE`, `COMMAND_HELP`, summaries) — same as
  `omarchy --help`
- Any MCP/`rpc` JSON payload (labels stay English; the window localizes
  them at render)
- Time storage (`HH:MM`) and time *input* (`h:mm AM/PM`)

## Translating

Copy the pattern from `i18n/es-MX.json`. Keep `%1`/`%2` holes, keep JSON
valid UTF-8, keep keys sorted (the extractor sorts; `test_i18n.sh`
enforces it). For counted strings, provide every category your language
needs — `plural_categories()` in the Lua module is the authority, and the
test checks it. Single-form languages (`ja`, `ko`, `zh`*, `th`, `vi`,
`id`, `ms`) only need `other`. A plain string is acceptable *only* for
those single-form languages on plural keys; everywhere else use the
object.

Start with the short chrome (`ui.*`, `help.*`, `footer.*`) so the window
is recognizable, then panels/sections, then `setting.*.description` (the
longest), then `cli.*` if you also want the CLI localized.
